# volatile 到底保证了什么

两个线程，各自把一个变量置 1，再去读对方那个变量，读到的值存进 x 和 y：

```text
初始  a = 0   b = 0

线程 1          线程 2
a = 1           b = 1
x = b           y = a
```

问题只有一句：**(x, y) 会不会两个都是 0？**

把 `(0,0)` 展开成四条"先后"关系，就能看出它为什么自相矛盾：

```text
a = 1  先于  x = b    线程 1 的程序顺序
x = b  先于  b = 1    x 读到 0，说明读的时候 b = 1 还没生效
b = 1  先于  y = a    线程 2 的程序顺序
y = a  先于  a = 1    y 读到 0，同理
```

一路推下去得到"`a = 1` 先于 `a = 1`"。顺序一致要求所有线程看到同一个全局顺序，不允许
这种环，所以 `(0,0)` 不可能。

弱内存模型不要求全局同一个顺序，这四条可以同时成立 —— 于是 `(0,0)` 会出现，而且真能
测出来。这个实验叫 Store Buffering。

## 一轮是怎么跑的

1. 主线程把 `a`、`b` 清零
2. 主线程和两个 worker 在闸门 1 对齐 —— 保证清零对两个线程可见
3. 线程 1 做 `a = 1; x = b;`，线程 2 做 `b = 1; y = a;`
4. 三方在闸门 2 对齐 —— 保证两个线程都做完了
5. 主线程看 `x`、`y` 是 0 还是 1，记一笔

跑 100 万轮，四种结果各自记账：

| 结果 | 含义 |
|---|---|
| `(0,0)` | 两个线程都在对方写生效之前读完了 —— **只有弱内存模型允许** |
| `(0,1)` | 线程 1 读到旧值，线程 2 读到新值 |
| `(1,0)` | 线程 1 读到新值，线程 2 读到旧值 |
| `(1,1)` | 两个都读到新值 |

## 代码在哪看

`sb.c` 一共 165 行。三个函数在第 42–74 行，上下相邻，每个两条分支、各两条语句，
唯一的差别是内存序：

| 函数 | 两个访存 | `(0,0)` |
|---|---|---|
| `relaxed` | `memory_order_relaxed` | 允许 |
| `seq_cst` | `memory_order_seq_cst` | 禁止 |
| `with_volatile` | `volatile int` 普通读写 | 会出现，但整段程序是 data race（UB） |

第 76 行往后是闸门和统计循环，跟内存序无关，可以先跳过。

`Sb.java` 是同一个实验的 Java 版。C 的 `volatile` 和 Java 的 `volatile` 是两回事：
C 的那个只保证"别把访存优化掉"，Java 的才真的带内存语义。这是全仓库最值得记住的一条。

那 `volatile` 该用在哪：MMIO 寄存器、信号处理里的 flag、`setjmp` 之后的局部变量 ——
都是"别被优化掉"，不是"线程间同步"。

## 跑

```bash
make run        # C 版，三种实现各 100 万轮，约 2 秒
make run-java   # Java 版，需要 JDK
make asm        # 生成 sb.s，看三个实现的机器码差别
```

## 输出

```text
# (x,y): x = 线程1读到的 b，y = 线程2读到的 a  |  每轮 1000000 次
relaxed  (0,0)=24852     2.5%   (0,1)=429580  (1,0)=431422  (1,1)=114146
seq_cst  (0,0)=0         0.0%   (0,1)=368469  (1,0)=454470  (1,1)=177061
volatile (0,0)=25516     2.6%   (0,1)=437497  (1,0)=413017  (1,1)=123970

seq_cst 一次 (0,0) 都没有。relaxed 和 volatile 有。
```

看 `relaxed` 那一行：100 万轮里有 24852 轮，两个线程都读到了旧值。`seq_cst` 一轮都没有。

## 看汇编

`make asm`，`gcc -O2 -masm=intel` 的结果，三个函数各贴一条路径：

```asm
# relaxed —— 一条 mov 存、一条 mov 读，没有任何 fence
mov  DWORD PTR b[rip], 1
mov  eax, DWORD PTR a[rip]

# seq_cst —— 存变成 xchg，隐含 lock，全栅栏
mov  eax, 1
xchg eax, DWORD PTR b[rip]
mov  eax, DWORD PTR a[rip]

# volatile —— 和 relaxed 逐字相同
mov  DWORD PTR vb[rip], 1
mov  eax, DWORD PTR va[rip]
```

`volatile` 那版生成的机器码和 `relaxed` 完全一样：访问没被优化掉，这就已经是它的全部
作用；它不提供原子性，也不建立 happens-before。

## 两个坑

- **别拿两种实现的百分比横比。** 数字随机器、编译器、负载大幅变化，`(0,0)` 在不同机器
  上从 0.8% 到 11% 都见过。能确定的只有"`seq_cst` 一次都没出现"这一条。Java 的 `plain`
  比例甚至每次运行都不同，取决于 JIT 当次怎么编译。
- **内存序必须是编译期常量。** 把它做成函数参数，编译器无法常量折叠，会保守地生成
  `xchg`，`relaxed` 就退化成 `seq_cst`。`make asm` 里 relaxed 路径一旦出现 `xchg`，
  就是退化了。
