# volatile 能拿来让两个线程同步吗？

不能。这个仓库跑给你看。

## 你可能写过这样的代码

```c
volatile int ready = 0;   // 线程 A 干完活，把它设成 1
int data = 0;             // 线程 B 一直等 ready 变成 1，然后读 data
```

很多人被告知：变量前面加个 `volatile`，两个线程就安全了。

这个说法只对了一半，下面有个两秒钟能跑出来的反例。

## 实验本身

两个线程，各自写一个变量，再去读对方那个变量：

```text
线程 1          线程 2
a = 1           b = 1
x = b           y = a
```

如果每条语句都老实按写的顺序发生，两个线程不可能同时读到 0 —— 线程 1 读 b 之前已经写过
a，线程 2 读 a 之前已经写过 b。

但实际跑起来，有些写法能测出"两边都读到 0"。跑 100 万轮，看是哪几种。

## 跑一下

```bash
make run
```

两秒，输出三行：

```text
x = 线程1读到的 b，y = 线程2读到的 a。每种写法各跑 1000000 轮。

volatile  两边都读到 0：8844    次 (0.9%)   只有一方读到 1：401327  / 554520    两边都读到 1：35309
relaxed   两边都读到 0：18150   次 (1.8%)   只有一方读到 1：491643  / 404203    两边都读到 1：86004
seq_cst   两边都读到 0：0       次 (0.0%)   只有一方读到 1：410566  / 402707    两边都读到 1：186727

只有 seq_cst 一次都没有。volatile 和 relaxed 都有。
```

只看每行第一个数字就够：

| 写法 | 100 万轮里"两边都读到 0" |
|---|---|
| `volatile` | 8844 次 |
| `relaxed` | 18150 次 |
| `seq_cst` | **0 次** |

## 为什么会这样

你写的是"先写 a，再读 b"。但编译器可以把这两条调换，CPU 也可以。

`volatile` 只挡住其中一件事：编译器不能把这条读写删掉、也不能把它塞进寄存器里省掉。
它不拦"调换顺序"，所以两次读仍然可能都发生在两次写之前。

## 那该怎么办

| 语言 | 正确写法 |
|---|---|
| C | `_Atomic` + `memory_order_seq_cst` |
| Java | 直接用 `volatile` 就对 |
| 都行 | 用锁，最不容易出错 |

注意 C 的 `volatile` 和 Java 的 `volatile` 是**两个不同的东西**，名字一样纯属巧合。
Java 那个真的管顺序，C 这个不管。这也是很多人踩坑的原因。

## 那 volatile 到底该用在哪

- 硬件寄存器地址：读一次就得真读一次，不能被合并或缓存
- 信号处理函数里用来通知的变量
- `setjmp` 之后还要继续用的局部变量

共同点是"别让编译器把它优化掉"，没有一条跟线程同步有关。

## 代码在哪看

`volatile.c` 一共 196 行。三种写法在第 50–92 行，上下挨着，每个四条语句，唯一的差别是
中间那两行的写法。第 94 行往后标了「脚手架」，和结论无关，可以先跳过。

`Volatile.java` 是同一件事的 Java 版，只有两种写法：普通字段和 `volatile` 字段。

## 想再深一点

用 `make asm` 生成 `volatile.s`，找"写 b、读 a"那两条指令：

```asm
# 加了 volatile
mov DWORD PTR vb[rip], 1
mov eax, DWORD PTR va[rip]

# 什么都不加
mov DWORD PTR b[rip], 1
mov eax, DWORD PTR a[rip]
```

两段指令一模一样，`volatile` 一个字节的额外指令都没生成 —— 它做的只是"别优化掉"。

再看要求了顺序的那一版：

```asm
mov  eax, 1
xchg eax, DWORD PTR b[rip]   # ← 多出这条。xchg 会强制先把 b 写出去
```

差别就在这一条 `xchg` 上。"两边都读到 0"这个现象消失，也是因为它。

## 一个提醒

别拿上面那几个百分比互相比较。它们随机器、编译器、负载变化很大 —— 同一份代码换台机器，
这个数字能从 0.9% 变成 11%。能确定的只有一条：`seq_cst` 一次都没出现。
